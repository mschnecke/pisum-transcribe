## 2. Engine: return to Vulkan after an out-of-memory error

- [x] 2.1 Add a flag to `LoadWorkItem` that marks a return (design D4). In the worker's load branch, a return that no newer load replaced disposes the engine without clearing `_model`, `_activeBackend` and `_maxInputDuration`, and doesn't set `_backendPreference`. Then it calls `Load(model, Auto, generation)`. Loads from `LoadAsync` keep their current handling. Only if task 1.2 found different `MaxAudio` values: the return sets `_maxInputDuration` to the smaller of the CPU limit and the limit of the Vulkan engine that failed, until it publishes its engine. Verify: all existing `TranscribeCppTranscriberTests` pass unchanged.
- [x] 2.2 In `Run`, keep the status of the Vulkan run's `NativeEngineException`. Once the failed request has been handled (it returned a result, failed with an error that isn't a backend error, or was cancelled by its caller), queue the return with the current load generation if the error was `ErrOom` on Vulkan with backend `auto`, the engine is `Ready` on the CPU for the failed run's generation, and the application isn't stopping (design D2, D4). Neither the status nor the load generation changes when the return is queued. `Classify` stays unchanged. Verify these new unit tests pass, along with the existing ones:
  - `TranscribeAsync_AutoOnVulkanOutOfMemoryOnLongClip_RetriesOnCpuThenReturnsToVulkan`: a 300 s request fails on Vulkan with `ErrOom`. The native call sequence is: Vulkan run, CPU load, CPU warm-up, CPU run, Vulkan load, Vulkan warm-up. The request returns the CPU text. `StatusChanged` reports `Loading`, `Ready`, `Ready`, and `ActiveBackend` goes from `CPU` to `Vulkan`, with no `Loading` in between. A later 10 s request runs on Vulkan.
  - `TranscribeAsync_AutoOnVulkanOutOfMemory_QueuedRequestRunsOnCpuBeforeReturn`: a request queued behind the failed one runs on the CPU before the Vulkan load.
  - `TranscribeAsync_DuringReturnToVulkan_IsAcceptedAndRunsOnVulkan`: a request submitted while the Vulkan load blocks is accepted, and runs on Vulkan after the load.
  - `TranscribeAsync_VulkanFailsDuringReturn_WaitingRequestRunsOnCpu`: the Vulkan warm-up of the return fails with `ErrBackend`, the status ends `Ready` (CPU), and a request that waited for the return runs on the CPU.
  - `TranscribeAsync_LoadFailsOnBothBackendsDuringReturn_IsFailedAndRejectsWaitingRequest`: the status is `Failed`, and the waiting request ends with `TranscriberNotReadyException` naming `Failed`.
  - `TranscribeAsync_BackendChangeDuringReturn_RejectsWaitingRequestAndEndsReadyOnCpu`: `LoadAsync` with `Cpu` while the return's Vulkan load blocks raises `Loading` at once. The waiting request ends with `TranscriberNotReadyException` naming `Loading`, the status ends `Ready` (CPU), and `Ready` on Vulkan is never raised.
  - `TranscribeAsync_BackendChangeBeforeReturnStarts_SkipsReturnAndRunsWaitingRequestOnCpu`: `LoadAsync` with `Cpu` while the return is still queued behind a request makes the worker skip the return. That request runs on the CPU engine before the newer load.
  - `TranscribeAsync_AutoOnVulkanBackendErrorOnLongClip_StaysOnCpu`: the same 300 s request with `ErrBackend` makes no Vulkan load after the CPU run.
  - `TranscribeAsync_ForcedVulkanOutOfMemory_IsFailedWithoutReturn`: backend `vulkan` with `ErrOom` is `Failed`, with no further load.
  - `TranscribeAsync_AutoOnVulkanOutOfMemoryAndCpuRetryBackendError_IsFailedWithoutReturn`: the status is `Failed`, with no Vulkan load.
