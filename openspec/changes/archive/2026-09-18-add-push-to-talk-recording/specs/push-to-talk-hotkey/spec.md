## Purpose

Defines the system-wide hold-to-talk key combination that signals when the user starts, finishes or abandons speaking, in whatever application has focus.

## ADDED Requirements

### Requirement: Hotkey setting
The application SHALL persist the push-to-talk hotkey as `recording.hotkey`: a non-empty set of keys. The default SHALL be the right Ctrl key alone. A missing, empty or unrecognizable value SHALL be replaced by the default, and a warning SHALL be logged.

#### Scenario: Default hotkey
- **WHEN** no hotkey has been saved
- **THEN** the push-to-talk hotkey is the right Ctrl key

#### Scenario: Invalid hotkey in settings
- **WHEN** the settings file contains a hotkey with an unknown key name
- **THEN** the hotkey is the right Ctrl key
- **AND** a warning is logged

### Requirement: Global detection
The hotkey SHALL be detected system-wide while any non-elevated application has focus, including when no Pisum Transcribe window is open.

#### Scenario: Hotkey in another application
- **WHEN** a text editor has focus and the user holds the hotkey
- **THEN** a push-to-talk *pressed* signal is raised

### Requirement: Press signal
A *pressed* signal SHALL be raised once when all keys of the hotkey are held down, regardless of the order in which they were pressed.

#### Scenario: Single-key hotkey held
- **WHEN** the hotkey is right Ctrl and the user presses right Ctrl
- **THEN** exactly one *pressed* signal is raised

#### Scenario: Multi-key hotkey pressed in any order
- **WHEN** the hotkey is Ctrl+Win and the user presses Win first and then Ctrl
- **THEN** exactly one *pressed* signal is raised

### Requirement: Auto-repeat ignored
Repeated key-down events generated by holding a key SHALL NOT raise additional *pressed* signals.

#### Scenario: Key held for several seconds
- **WHEN** the user holds the hotkey for 5 seconds and keyboard auto-repeat generates repeated key-down events
- **THEN** only one *pressed* signal is raised

### Requirement: Release signal
After a *pressed* signal, a *released* signal SHALL be raised once, when the first of the hotkey keys is released.

#### Scenario: User releases the hotkey
- **WHEN** a *pressed* signal was raised and the user releases right Ctrl
- **THEN** exactly one *released* signal is raised

### Requirement: Cancel signal on other keys
After a *pressed* signal, pressing any key that is not part of the hotkey SHALL raise a *cancelled* signal instead of a later *released* signal. Releasing the hotkey afterwards SHALL NOT raise *released*.

#### Scenario: User types a shortcut with the hotkey modifier
- **WHEN** the hotkey is right Ctrl and the user presses right Ctrl and then C
- **THEN** a *cancelled* signal is raised
- **AND** no *released* signal is raised when right Ctrl is let go

### Requirement: Keys pass through
The hotkey detection SHALL NOT block or alter the key events that other applications receive.

#### Scenario: Shortcut still works in focused application
- **WHEN** the hotkey is right Ctrl and the user presses right Ctrl+C in a text editor
- **THEN** the text editor performs its copy action

### Requirement: Simulated key events ignored
Key events simulated by software, including the application's own text insertion and key remapping tools, SHALL NOT raise, release or cancel the hotkey.

#### Scenario: Simulated paste with a matching hotkey
- **WHEN** the hotkey is left Ctrl and the application simulates Ctrl+V
- **THEN** no *pressed* signal is raised

#### Scenario: Simulated key while holding
- **WHEN** a *pressed* signal was raised and another application simulates a key press before the user releases the hotkey
- **THEN** no *cancelled* signal is raised

### Requirement: Key events stay private
The application SHALL use keyboard events only to detect or configure the push-to-talk hotkey. It SHALL NOT keep key events beyond the current hotkey state, and SHALL NOT write keys, key codes or typed characters to disk or logs, except the configured hotkey.

#### Scenario: Typing while the app runs
- **WHEN** the user types text in another application while Pisum Transcribe runs
- **THEN** the log contains no entry naming the typed keys
- **AND** no file created by the application contains them

#### Scenario: Cancel by another key
- **WHEN** the hotkey is right Ctrl and the user presses right Ctrl and then C
- **THEN** the logged cancel entry does not name the C key

### Requirement: Reset on session switch
When the Windows session is locked, unlocked or switched, the hotkey state SHALL reset. A hotkey considered held SHALL raise *cancelled*.

#### Scenario: Screen locked while holding
- **WHEN** a *pressed* signal was raised and the user locks the workstation before releasing the key
- **THEN** a *cancelled* signal is raised
- **AND** after unlocking, the next press of the hotkey raises *pressed* normally

### Requirement: Missed release recovery
When the hotkey is considered held but its keys can no longer be observed as held, the hotkey state SHALL reset within 1 second, and a hotkey that raised *pressed* SHALL raise *cancelled*. This covers key releases the application cannot see, for example while an elevated window, the UAC prompt or the lock screen has focus.

#### Scenario: Elevated window takes focus while holding
- **WHEN** a *pressed* signal was raised and an elevated window takes focus before the user releases the hotkey
- **THEN** a *cancelled* signal is raised within 1 second
- **AND** the next press of the hotkey raises *pressed* normally

#### Scenario: Normal release
- **WHEN** a *pressed* signal was raised and the user releases the hotkey while a non-elevated application has focus
- **THEN** a *released* signal is raised
- **AND** no *cancelled* signal is raised
